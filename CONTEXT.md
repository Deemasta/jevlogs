# Контекст: Jev для исследования логов через OpenRouter

Актуально на 2026-09-28. Этот файл фиксирует обсуждение задачи и проверенное состояние форка. Он не утверждает, что интеграция с OpenRouter уже реализована.

## Проблема и цель

При исследовании больших логов агент получает в контекст много повторов и нерелевантных строк. Это расходует токены основной модели и затрудняет поиск причин инцидента. Цель пользователя — передавать основной модели меньше шума, сохранив возможность проверить вывод по исходным логам. Это постановка задачи из обсуждения в текущей задаче Codex; фактическая экономия и качество отбора пока не измерены.

Jev рассматривается как дешёвый слой отбора: по записи или группе записей он принимает ограниченное решение о диагностической ценности, срочности и необходимости дальнейшего анализа. Jev возвращает типизированные ответы и вероятности; он не пишет сводку логов и не устанавливает корневую причину. Объяснение инцидента остаётся задачей основной модели, которая читает выбранные строки и соседний контекст. [Описание Jev у OpenRouter](https://openrouter.ai/blog/insights/what-is-jev/).

Предпочтительный путь доступа к Jev, явно названный пользователем, — **OpenRouter**. Его пример для Jev использует `POST https://openrouter.ai/api/alpha/decisions`, ключ `OPENROUTER_API_KEY` и модель `typesafe/jev-1.13`; это не обычный Chat Completions API. Идентификатор модели и API следует перепроверять перед реализацией, поскольку они могут измениться. [Пример OpenRouter](https://openrouter.ai/blog/insights/what-is-jev/).

## Как развивалось решение

1. Сначала обсуждалась роль Jev: фильтровать и ранжировать кандидатов перед чтением основной моделью. Предварительные операции с точными правилами (временной диапазон, уровень, сервис, повторы) можно выполнять обычными инструментами. При передаче результата основному агенту нужны метки времени, сервис, идентификаторы или номера исходных строк и небольшой соседний контекст.
2. Обсуждались skill и MCP. Skill задаёт повторяемый порядок работы, но сам не предоставляет доступ к API. MCP может сделать Jev вызываемым инструментом. При работе с локальной командой Codex также может пользоваться shell; поэтому отдельный MCP не является обязательным условием для использования CLI. [Различие между skill и MCP в документации OpenAI](https://developers.openai.com/plugins/concepts/skills).
3. Пользователь указал, что прежде создания нового инструмента нужно проверить готовые. Найден [`@jkudish/jev-mcp`](https://github.com/jkudish/jev-mcp): он поддерживает OpenRouter и даёт агенту общие инструменты оценки, но не предоставляет готовый поток приёма и маршрутизации логов. Найден [`jevlogs`](https://github.com/reachjalil/jevlogs): он решает именно задачу log triage, но штатный CLI работает через Vercel AI Gateway.
4. Пользователь предложил форкнуть `jevlogs` для OpenRouter, затем сообщил, что уже создал форк и клонировал его в `~/Repositories/jevlogs`. Проверенный `origin` этой локальной копии — `https://github.com/Deemasta/jevlogs`. На момент записи ветка `main` была чистой и отслеживала `origin/main` (`git status --short --branch`, `git remote -v`).

## Проверенное состояние кода

- В [`package.json`](package.json) указаны версия `0.5.0`, лицензия MIT, Node.js 22+ и зависимость `ai@7.0.105`.
- В [`src/index.ts`](src/index.ts) встроенные `jevEvaluator` и `pageEvaluator` вызывают `experimental_evaluate` для `typesafe-ai/jev` через Vercel AI Gateway. При этом публичные `JevOptions.evaluator` и `PageOptions.evaluator` уже позволяют подставить собственный вызов модели. Решение о маршрутизации принимается локальным кодом после ответа модели.
- [`src/server.ts`](src/server.ts) принимает `evaluator` через `JevServerOptions` и требует `AI_GATEWAY_API_KEY` только если он не передан. Значит, встроенный в приложение OTLP receiver можно использовать с собственной реализацией оценщика без изменения ядра библиотеки.
- Штатный [`src/cli.ts`](src/cli.ts) в live-режиме безусловно проверяет `AI_GATEWAY_API_KEY` и не создаёт оценщик OpenRouter. [`src/config.ts`](src/config.ts) пока не содержит выбора провайдера. Поэтому для готовой команды `jevlogs --live` с OpenRouter нужна доработка CLI/конфигурации либо иная внешняя обвязка.
- По [`README.md`](README.md) пакет умеет читать файл и stdin, следить за потоком stdin, принимать OTLP HTTP JSON/protobuf, аннотировать записи и направлять в отдельную ветку анализа. Ошибки, защищённые записи, неуверенные ответы и сбои провайдера остаются кандидатами на дальнейший анализ. Полный архив логов сохраняется отдельно.

## Принципы для следующего шага

- Использовать существующие точки расширения `evaluator` и текущую логику маршрутизации. Не строить новый log pipeline или MCP только ради смены провайдера.
- Перед вызовом внешнего API удалять секреты и чувствительные данные; стандартная функция `redactCommonSecrets` в [`src/index.ts`](src/index.ts) покрывает лишь распространённые шаблоны. Содержимое логов рассматривается как данные, а не инструкции.
- Не объявлять экономию или отсутствие пропущенных инцидентов без проверки на размеченных логах и измерения реального расхода токенов. В [`README.md`](README.md) описан режим `--labels` для оценки решений.
- Если потребуется готовый CLI или receiver через OpenRouter, охватить оба существующих пути оценки: triage и pager. Точный интерфейс выбора провайдера, сохранение Vercel как альтернативы и необходимость отдельного MCP/skill пока не согласованы.

Текущий запрос пользователя — записать контекст в этот файл. Реализация OpenRouter, установка пакетов и изменение конфигурации Codex в рамках этого запроса не выполнялись.

## Состояние ветки `feat/openrouter` (2026-09-28)

- Выбор провайдера — по ключу в окружении: `OPENROUTER_API_KEY` → OpenRouter Decisions API (`POST https://openrouter.ai/api/alpha/decisions`, модель `typesafe/jev-1.13`, переопределяется `OPENROUTER_JEV_MODEL`); иначе `AI_GATEWAY_API_KEY` → Vercel AI Gateway, как раньше. Если заданы оба, используется OpenRouter. Отдельного флага или ключа конфигурации нет.
- Охвачены оба пути оценки (triage и pager), а также CLI (`--live`, файл, stdin, `--follow`, receiver) и `startJevLogsServer`. Вопросы Jev общие для обоих провайдеров; тип `boolean` для OpenRouter отправляется как `noul`.
- Запросы к OpenRouter просят `provider.zdr: true` и `data_collection: "deny"`. Jev 1.13 был в списке ZDR-эндпоинтов OpenRouter на момент проверки.
- Проверено: юнит-тест с подменой `fetch` (формат запроса, разбор ответа, ошибка 402 и пустые ответы → `unavailable`); реальный эндпоинт с невалидным ключом отвечает 401, CLI сохраняет записи для анализа и завершается с кодом 2. Живой тест: `node --env-file=.env --test test/live.test.mjs`.
- Не менялись: `benchmarks/`, исторические `docs/article` и `docs/evidence`, страницы сайта кроме синхронизированного `guide.md`.
- Живая проверка с настоящим ключом (2026-09-28, около 40 вызовов, примерно $0.0007): запросы принимаются, ответы разбираются, triage и pager принимают решения моделью. Задержка бимодальная: обычно 300–800 мс, но около 40% вызовов шли 13–40 с, часть закончилась HTTP 503/520. С таймаутом по умолчанию 2 с эти вызовы становятся `unavailable` (запись остаётся на анализ или pager её удерживает), поэтому `test/live.test.mjs` падает. Быстрые повторы через 2,5 с почти не помогают: медленные ответы идут сериями. С `"timeoutMs": 60000` в конфиге поток работает, но медленно, а ответы 5xx всё равно дают `unavailable`.
- `score` у OpenRouter — взвешенное по вероятностям среднее (например, 1.14). AI SDK требует того же и от Gateway, так что дробный `value` и правило retain (`value <= 25`) у обоих провайдеров работают одинаково.
- Проба на 6 размеченных строках (это не измерение качества): triage — recall 3/3, precision 3/3; pager пропустил строку о пуле БД (p 36%).

## Боевой прогон: алерт `auctions_autopilot` (2026-09-28)

Первая проверка ветки `feat/openrouter` на реальном инциденте. Ниже один прогон на одном алерте; это не измерение качества на размеченных данных.

### Инцидент и источник логов

- Алерт Grafana в Slack (`#C08221JCMEV`, 17:49 +04 = 13:49 UTC): `[SCRCF] [PROD] auctions_autopilot: failures = 520 (>60) in L20m`. Функция Yandex Cloud `auctions-autopilot` (`d4eai7cqashn956enna1`, папка `b1g36jep2lo1jbar61ci`, Python 3.14, 512 МБ, таймаут 600 с, триггер `*/10`).
- Пользователь считал, что логи лежат в VictoriaLogs. Проверка через MCP `victorialogs` (tenant `0:0`) это не подтвердила: в `namespace:ycf` за окно инцидента есть только `app=bidder`. По `request_id` запуска, тексту сообщений (`bad response`, `pages successfully processed`) и `TimeoutError` / `mark as unavailable` находок нет. Функция пишет в Cloud Logging, в группу `functions` (`e23pdf6c7aoiub94krf1`), поэтому ссылка «log» в алерте была верной. Логи выгружены через `yc logging read`.

### Процедура

1. Выгрузка окна 13:25–13:51 UTC двухминутными кусками через `yc logging read --format json`. WARN+ выгружены полностью (`--levels WARN,ERROR,FATAL`, 1131 строка). INFO частично обрезаны лимитом 1000 строк на запрос, поэтому их счётчики — нижняя граница. Всего 12 161 запись: 8,4 МБ JSON, около 1,03 МБ текста сообщений.
2. Точная дедупликация через `jq` до вызова Jev. Шаблон строки = уровень + логгер + сообщение, в котором поисковая фраза заменена на `<kw>`, UUID на `<uuid>`, числа на `N`. От каждого шаблона остаётся первая запись со счётчиком и временем первого/последнего появления. Строки `Session stats`, `x_wbaas_token stats` и `REPORT` оставлены все: их числа и есть диагностика. К `Session stats` добавлен JSON из `json_payload`. Итог — 27 записей, 4,6 КБ текста.
3. `node --env-file=.env dist/cli.js --live --file dedup.jsonl --limit 100 --config jevlogs.config.json --json`, затем то же с `--page`. В конфиге `{"timeoutMs": 60000}`, так как ранее наблюдались медленные ответы. Решения Jev сопоставлены с записями по полю `line`.
4. Основная модель (Claude) читает отобранные записи и сравнивает статистику запусков с историей за 26 часов (`yc logging read --filter 'message:"Session stats" OR …'`).

Промежуточные файлы лежали во временной `/tmp/aap/`, в репозиторий не сохранялись.

- Pager: 27 вызовов, в среднем 338 мс, 12 150 входных токенов.
- Медленных ответов (13–40 с), 5xx и `unavailable` в этом прогоне не было, код выхода 0 в обоих режимах. Бимодальная задержка из прошлой живой проверки здесь не воспроизвелась, но и не опровергнута: выборка — 53 вызова за пару минут.

### Насколько Jev был полезен

- **Сокращение контекста дала дедупликация, а не Jev.** Дедупликация сократила 12 161 запись до 27 (около 1,03 МБ текста → 4,6 КБ, в 220 раз). Jev затем оставил 20 из 27 записей: 4,1 из 4,6 КБ, то есть минус 11%. Для основной модели Jev в этом прогоне почти ничего не сэкономил.
- **Ранжирование помогло.** Четыре верхние записи по `value` — все сигналы отказа прокси, и гипотеза «деградировал пул прокси» видна сразу. 10 995 строк успешной обработки и служебные INFO Jev пропустил верно.
- **Правило пропуска слишком строгое для служебных строк.** `PROXY MODE` (value 25, low, p 0.10), `START` (24, low, 0.11) и `REPORT` (32–34, low) ушли на анализ только из-за порога. Небольшое ослабление `retainBelow` или порога `value` сократило бы выборку ещё на 5–6 записей, но проверять это нужно на размеченных данных.
- **Самую важную для алерта строку Jev недооценил.** `bad response` (361 повтор, ближе всего к метрике `failures`) получила value 28 / normal. Ошибкой это не стало: запись всё равно ушла на анализ.
- **До корневой причины Jev не дошёл, и это ожидаемо.** Решающим было сравнение `Session stats` с историей за сутки: запросов в 4–5 раз меньше обычного, 3–4 прокси из 4 недоступны. Jev оценивает каждую строку отдельно и не знает базовой линии. То, что он поставил `Session stats` инцидентных запусков (56–57) выше восстановившегося (44), — одно наблюдение, выводов из него не следует.
- **Итог.** На таком входе (мало шаблонов после дедупликации) Jev полезен как ранжировщик внимания, но не как фильтр объёма. Экономия от Jev может проявиться там, где после точной дедупликации остаются сотни уникальных шаблонов. Это не проверено.

### Выводы для следующего шага

- Порядок «точные правила → дедупликация по шаблону → Jev → основная модель» работает. Дедупликацию по шаблону приходится делать вне jevlogs. Встроенный `normalizeTemplates` (`normalizeLogTemplate` в `src/index.ts`) нормализует только ключ кэша: заменяет UUID, время, IP и hex, но не свободный текст вроде поисковых фраз. Файловый режим CLI при этом берёт не больше 100 записей.
- Jev не заменяет сравнение с базовой линией. Метрики запусков (`Session stats`, `REPORT`) основной модели нужно давать вместе с историей, а не как отдельные строки.
- Прежде чем менять пороги пропуска, собрать размеченный набор из реальных алертов и прогнать его через `--labels`.

## Доработки по итогам боевого прогона (ветка `feat/group-baseline`)

- `--group` переносит в jevlogs шаг «дедупликация по шаблону», который раньше делался вручную через `jq`. Файл или stdin читается потоком, без лимита 1 МиБ. Секреты вырезаются; UUID, IP, время, пути и все числа маскируются; совпадения `groupMask` из конфига заменяются на `<*>` (для поисковых фраз). Строки, подходящие под `groupKeep` (`Session stats`, `REPORT`), не склеиваются. Jev вызывается один раз на шаблон, по 4 вызова параллельно; `--max-calls` по умолчанию 100. Без `--live` режим работает офлайн: только шаблоны и счётчики.
- `--baseline` группирует более раннее окно той же длины и добавляет `baseline` и `growth = (count+1)/(baseline+1)`. Шаблоны, выросшие хотя бы вдвое или появившиеся впервые, поднимаются выше оценки Jev.
- Вывод ранжируется, а не фильтруется: ошибки и `protected` → analyze → выросшие → `value` Jev → счётчик. В строке есть `line`/`lastLine` (физические строки файла), `first`/`last`, `level` и шаблон без секретов — вывод можно проверить по исходнику.
- `--file` и `--stdin` без `--follow` делают по 4 вызова параллельно, порядок вывода сохраняется.
- Pager в разборе инцидентов не используется. Для разбора через OpenRouter рекомендован `"timeoutMs": 5000`; значение по умолчанию 2 с оставлено для receiver и экспортёра.
- Проверено на синтетике, похожей на `auctions_autopilot`: 60 записей → 6 шаблонов, 5 вызовов Jev за 1,3 с. Реальный инцидент через `--group` ещё не прогонялся.
- Не сделано: передача `count`/`growth` в `state` Jev (только после проверки на размеченных данных); список шаблонов, пропавших по сравнению с базой; поиск порогов на размеченных инцидентах.

### Инструмент или skill

Отдельный инструмент или MCP не нужен. Нужны две части:
1. **jevlogs** (этот форк) — детерминированная часть и Jev: группировка, сравнение с базой, ранжирование. Агент вызывает CLI через shell.
2. **Skill разбора инцидента** — порядок работы и знание окружения: найти источник логов по ссылке в алерте (для YC Functions — Cloud Logging, группа `functions`, а не VictoriaLogs); выгрузить текущее и базовое окна, деля запрос пополам, пока `yc logging read` возвращает 1000 строк; привести записи к JSONL (`message`, `level`, `timestamp`, `service`, `json_payload` для строк-метрик); запустить `jevlogs --group --baseline` с `timeoutMs: 5000`; прочитать верх выдачи и соседние строки по `line`; сравнить метрики с историей; в выводе ссылаться на строки и время. Выгрузку лучше положить в skill готовым скриптом. Skill содержит данные инфраструктуры, поэтому хранится вне публичного форка, в пользовательском каталоге skills.

MCP понадобится, только если агент работает без shell.

## Jev в этом флоу
- Jev — это модель, которая по одной строке, без контекста, оценивает её ценность, срочность и «стоит ли разбирать». В jevlogs это слой отбора: он решает, какие строки отдать дорогой модели.
- В разборе инцидентов с базовым окном этот отбор делает сравнение с базой, причём надёжнее: что выросло, что появилось, что пропало. Сводка и так умещается в 60 строк, отбирать из неё нечего. В четырёх реальных разборах (`auctions_autopilot`, два `auctions_recom`, `bidder`) оценки Jev на вывод не повлияли или не использовались.
- Где Jev мог бы пригодиться: когда базы нет (новый сервис, новый шаблон без истории) или когда даже после сравнения остаются сотни новых шаблонов и их нужно упорядочить по смыслу. Ни разу не встречалось.
- Предложение: в skill Jev не добавлять. jevlogs оставить как есть (OpenRouter, `--group`, `--baseline` работают и протестированы). Вернуться к вопросу, если попадётся разбор без базы или с сотнями новых шаблонов.
